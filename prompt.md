## 5. Study content pipeline

`scripts/generate-lessons.ts` — run once, then on demand per task.

For each of the 26 ECO tasks, retrieve the mapped source slices and produce a lesson with these sections:

1. **What this task actually is** — 200–300 words, plain language.
2. **Where it sits in PMBOK 8** — which performance domain, which named processes, which focus areas.
3. **Predictive framing** and **Adaptive/hybrid framing** — side by side. This matters because ~60% of the exam is adaptive or hybrid.
4. **Artifacts and authority** — every artifact this task touches, each tagged with its document bucket: *business document* (PM cannot change), *project management plan component* (needs CCB/management approval), or *project document* (PM updates freely).
5. **Exam traps** — 5–8 specific ways PMI sets up a wrong answer here.
6. **Worked example** — one realistic scenario reasoned through out loud.
7. **12 flashcards** — front/back, mixed between recall, discrimination ("X or Y?"), and application.

Write each lesson to `lessons` with `reviewed = false`. The app shows an unreviewed badge until I tick it off.

**Correct the four structural errors that most prep material still carries.** Bake these into the generator's system prompt as facts:

- Quality is **not** a performance domain — *Manage Quality Assurance* is a Governance process.
- Procurement is **not** a performance domain — *Plan Sourcing Strategy* is a Governance process; detail lives in Appendix X4.
- Communications is folded into the **Stakeholders** domain (3 of its 7 processes).
- Qualitative and quantitative risk analysis are **merged** into one *Perform Risk Analysis* process.

## 6. Question generation engine — the heart of this app

### 6.1 Generator contract

`scripts/generate-questions.ts --task <id> --count <n> --difficulty <1|2|3>`

Structured JSON output only. Reject and retry any response that fails schema validation (zod). Max 2 retries, then quarantine with `status = 'failed'`.

### 6.2 The PMI mindset, encoded

Put these in the system prompt verbatim. They are the rules the *correct* answer must satisfy and the *distractors* must violate:

1. **Be proactive.** The PM acts before the problem lands. Options that wait, watch, monitor, or revisit after go-live are wrong.
2. **Be responsible.** Solve at your own level first. Escalating to the sponsor, PMO or management is never the first move — it is what happens after analysis has exhausted the PM's authority.
3. **RARA** — Record → Analyze → Review → Act. For *"what should the PM do?"*, the best option covers the most of that cycle.
4. **ARA for FIRST/NEXT.** For *"what should the PM do FIRST"* or *"NEXT"*, drop Record: understand before acting. The first move is almost never a decision, a change request, or a conversation with the sponsor.
5. **Read the verb.** *May · might · could* = a risk that has not happened → risk register, risk response planning. *Will · has · is* = an issue that is real → issue log, corrective action. Stems must use these verbs consistently and deliberately.
6. **Three buckets.** Business documents (business case, benefits management plan) — the PM cannot change them. Project management plan — CCB or management approval required. Project documents — PM updates freely.
7. **Baseline touched → change request.** No exceptions, however sensible the shortcut sounds. Contingency reserve funds identified *risks*, never a scope change.
8. **Never invent process.** If the stem does not say a register, plan, CCB or process exists, the correct answer may not assume one. The generator must not write a stem whose answer depends on an unstated fact.
9. **Proportionate response.** "Mitigate across all workstreams", "re-plan the whole project", "diversify everything immediately" — overcorrection is wrong, and so is its opposite.
10. **Role boundary.** When stakeholders are divided and ask the PM for a recommendation, the answer is *analyse and present options* — never pick one and execute. (This is my one recorded miss; over-represent it.)

### 6.3 Question schema

Every generated question carries:

```
eco_task_id, domain, delivery_approach: predictive|adaptive|hybrid,
item_type: single|multi|matching|ordering|calculation|graphic|case,
difficulty: 1|2|3,
style: what_should_pm_do|first|next|best|concept|calculation,
stem, exhibit (optional), pmbok_ref,
options[]: { label, body, is_correct, distractor_family, rationale }
```

**Every option gets a rationale, including the correct one.** A right answer for the wrong reason fails the real exam.

**Every wrong option must be labelled with exactly one distractor family**, from this closed list:

`escalate_prematurely` · `wait_or_defer` · `act_without_analysis` · `overcorrect` · `complacent_aggregate_read` · `wrong_document_bucket` · `risk_issue_confusion` · `invented_process` · `wrong_delivery_approach` · `role_boundary_violation`

This is the single most important field in the schema. My mock reviews are scored by which family catches me, not by percentage — the analytics in Section 10 depend on it.

### 6.4 Runtime LLM use — only these three

1. **"Explain this differently"** on a question I got wrong — one call, cached against `question_id`.
2. **Top-up generation** when a task's unseen-question pool drops below 15 — queued, not blocking.
3. **Weekly coaching summary** — one call per week over my attempt data, producing a plain-language read of what's improving and what isn't.

Every call writes a `llm_usage` row with token counts and computed cost. A hard monthly cap (default $5) in `settings`; at 80% the UI warns, at 100% runtime generation stops and the app serves only the existing bank.

### 6.5 Bank composition target

Generate to these proportions, tracked on an admin page:

- **Domain:** Process 41% · People 33% · Business Environment 26%
- **Delivery approach:** ~40% predictive · ~60% adaptive and hybrid
- **Difficulty:** 25% / 50% / 25% across levels 1/2/3
- **Item types:** 55% single · 12% multi · 8% calculation · 10% graphic · 8% case · 7% matching/ordering
- **Minimum 120 questions per ECO task** before the bank is considered complete (~3,100 total). At current pricing this whole bank costs well under $2 to generate.

### 6.6 Graphic questions

For `item_type = graphic`, the generator emits an `exhibit` JSON spec, not an image. The app renders it with Recharts. Supported exhibit kinds: `burndown`, `burnup`, `network_diagram`, `control_chart`, `pareto`, `tornado`, `evm_dashboard`, `histogram`, `kanban`, `power_interest_grid`.

The question must require *reading a value off the exhibit and then deciding what a PM does about it*. The second half is what gets scored — never ask only "what is the value".

## 7. Automated question QA

Nothing enters the served bank without passing `scripts/qa-questions.ts`.

**Deterministic checks (cheap, run first):**

- Exactly one correct option for `single`; 2–3 for `multi`.
- Correct-answer position is randomised; across any batch of 50, no position exceeds 35%.
- Correct option is not the longest option more than 30% of the time.
- No option contains absolutes ("always", "never", "all") unless the correct answer does too.
- Near-duplicate detection against the existing bank (normalised trigram similarity > 0.85 → reject).
- No run of >25 words matching any file in `content/source/`.
- Every wrong option has a `distractor_family` from the closed list; every option has a rationale.

**LLM reviewer pass (second call, adversarial prompt):**

Ask a fresh call to *attack* the question: is there a second defensible answer? Does the stem leak the answer? Does the correct answer require a fact not in the stem (violating rule 8)? Does the tagged ECO task actually match the content? Verdict `pass` / `revise` / `reject` with reasons. `revise` goes back once; `reject` is quarantined.

Give me an admin review queue where I can approve, edit or bin quarantined questions by hand.
